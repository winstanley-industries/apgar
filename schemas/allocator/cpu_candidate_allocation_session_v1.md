# CPU Candidate-Allocation Session v1

CPU Candidate-Allocation Session v1 composes persistent CPU candidate-pool
preparation, the One-World and negotiated-price CPU references, bounded
targeted regeneration, and one terminal fixed-pool Multi-World search into a
self-contained Phase 4 contender result.

## Version, inputs, and ownership

Production accepts schema version `1`. One synchronous invocation receives
rvalue references to one exact Board Snapshot, its authentic
`MultiNetWorkload`, an associated `ResourceCapacityModel`, one
`PreparedCpuCandidatePools` result with the sole mutable CandidateStore, and a
semantic session configuration.

The inputs transfer into the move-only result only on success. On any error,
including a post-publication failure, they remain caller-owned. A targeted
failure observation whose CandidateStore-publication-committed bit is true
means that caller-owned store is authoritative and must be retained or
explicitly reconciled; the error never implies rollback.
The session error also retains a publication-committed bit. It becomes true
for a committed failed child or after any prior nonempty successful targeted
publication, including host or invariant failure during later session
composition. A failed session is not a completed replay artifact;
reconciliation must rebuild its successor pools from the authoritative store.

The successful session owns the Board, workload, capacities, preparation and
CandidateStore, final candidate pools, final One-World state, compact epoch
records, and terminal Multi-World execution. The terminal Multi-World result is
declared after the store-owning preparation, so reverse destruction releases
its retention lease first. Mutable CandidateStore access is not exposed by the
session.

## Configuration

The complete semantic configuration contains, in declaration order:

1. session schema, positive intrinsic-cost weight, and positive maximum
   targeted-regeneration epochs;
2. Negotiated Price State v1 configuration;
3. One-World allocator limits;
4. Targeted Regeneration Plan v1 configuration;
5. Targeted Regeneration Execution v2 configuration;
6. one or more terminal Multi-World schedules and Multi-World Execution v1
   configuration;
7. positive cumulative session limits for retained epoch records, planning
   visits, requested columns, route queries and work, policy projection
   visits, generated bytes, rejection bytes, and transient-result bytes; and
8. the session-authoritative known-unmapped-exact-conflict count.

The nested targeted and Multi-World conflict counts must be zero. The session
copies its authoritative value into each child call. Regeneration epochs are
capped at `1,000,000`; scalar cumulative work is capped at
`1,000,000,000,000,000`.

Terminal schedules require distinct nonzero keys, positive search weights and
round counts, and no duplicate exact weight/round pair. One schedule must be
the canonical one-round anchor whose search weight equals the session
One-World intrinsic weight. The maximum regeneration epoch count plus the
largest terminal schedule update count must fit the negotiated-price iteration
limit. Schedule order is nonsemantic. The session copies and sorts schedules
by key before execution, result storage, or checksum encoding.

## Association and source validation

Before state creation, the Board content hash, workload association, capacity
association, and prepared CandidateStore validity must agree. A count-only pass
first authenticates the complete pool and candidate roster. All bounds that do
not require candidate footprints are rejected before resource traversal. A
second pass then inspects candidate resource-span count, expanded physical-edge
uses, and the greatest selected resource footprint in each pool with widened
arithmetic and charged per-pass quotas. It stops at the first span or expanded
use outside the accepted envelope rather than scanning a rejected suffix.
Null candidates, overflow, incomplete pool rosters, net drift, endpoint/layer
drift, or candidate association drift fail through this session or the
composed reference before any regeneration query.

## Aggregate preflight

Let `E` be maximum regeneration epochs, `Q` maximum requested columns per
epoch, `W` per-query maximum CPU A* work, `R` maximum reconstruction states,
`P` source pool count, `C` source candidate count, `U` source expanded edge
uses, `K` CandidateStore maximum retained candidates per net, and `N` the
maximum negotiated-price records. Before the initial allocation, widened
arithmetic projects:

```text
maximum requested columns = E * Q
maximum route work = E * Q * W
maximum planning visits = E * maximum planning visits per epoch
maximum policy visits = E * maximum target nets per epoch
                          * maximum price records * 4
maximum generated bytes = E * Q * maximum candidate-draft bytes
maximum rejection bytes = E * Q * 4,096
maximum transient bytes = E * Q * (256 + 2 * 4,096)
maximum final candidates = min(P * K, C + E * Q)
maximum final expanded uses = U + E * Q * R
maximum policy entries in one epoch =
  min(execution maximum policy entries, Q * N + Q)
maximum retained rejection records = existing rejection records
  + E * (maximum final candidates + Q)
```

The one-epoch policy-entry projection feeds the same Targeted Regeneration
Execution v2 formulas for CandidateStore admission input bytes and exact
validation work, using the Board obstacle and terminal counts. Every value must
fit the corresponding session, One-World, CandidateStore snapshot/pin,
transaction item, input-byte, exact-work, and retained-rejection bound.
Equality is accepted; overflow and one-under fail before CPU routing or store
mutation. Targeted Regeneration Execution v2 independently rechecks its exact
plan at every epoch.
For a known resource-refinement session, `E` is zero because no regeneration
plan or query is permitted; hypothetical column, route, or draft work is not
reserved.

The terminal Multi-World worst-case preflight uses the maximum final candidate
count and spans, all configured schedules and rounds, and this resource-work
charge for one candidate-processing pass:

```text
One-World maximum resource records
  + sum over source pools of
      max(greatest current candidate expanded footprint, R)
```

The span upper bound is the current complete span count plus `E * Q * R`.
For `M` branch worlds and `P` nets, terminal storage is projected before the
initial allocation as:

```text
buffered and retained selection records = M * P
buffered and retained resource records =
  M * (One-World maximum resource records
       + sum over source pools of
           max(greatest current candidate expanded footprint, R))
buffered and retained price records = M * maximum price records
retained worlds = M
retained winner pins = min(maximum final candidates, M * P)
```

Every buffered, retained, world, and pin quantity must fit its independent
Multi-World cap. Known resource-refinement sessions use `M = 0` and `E = 0`,
but still execute and preflight Multi-World's bounded fixed source-
authentication pass; they charge no branch rounds, Pareto comparisons,
terminal branch records, or hypothetical regeneration transaction work.

After each exact targeted plan is built and before its first query, the session
also checks cumulative counters against the exact plan: planning visits,
columns, queries, route work, four complete price-roster policy passes,
generated bytes, rejection bytes, and transient-result bytes. Successful
runtime counters are then accumulated from the child execution. A failed
execution remains a typed session error and does not invent a completed epoch.

## Canonical execution

Build the initial complete negotiated-price state and immutable snapshot, then
run One-World over the prepared complete pools. If a known unmapped exact
conflict exists, skip targeted regeneration and retain
`resource_refinement_required`. If the initial world selects every net with
zero overuse, skip targeted regeneration and retain `feasible`.

Otherwise, for each bounded epoch:

1. Build one Targeted Regeneration Plan v1 from the current complete pools,
   current One-World allocation, and current negotiated-price state.
2. Prove the exact cumulative plan envelope fits before query one.
3. Execute Targeted Regeneration Execution v2 once. It runs bounded production
   CPU A*, publishes all of that plan's columns through one conditional CAN-004
   transaction, refreshes the complete pools and One-World selection at the
   plan's successor price snapshot, and hands off the successor lease before
   releasing the source lease.
4. Recreate the canonical successor pool manifest and retain one compact epoch
   record containing source/successor manifests and worlds, successor price,
   plan/execution identities, complete ordered column evidence, counters, and
   change predicates.
5. Replace the current price state, pools, world, and request before evaluating
   the next epoch.

V1 intentionally uses one common One-World regeneration lineage. It does not
publish columns between independent Multi-World branches. After regeneration
terminates, the final complete pools are frozen and passed once to fixed-pool
Multi-World Execution v1. That execution branches every schedule from the
single final negotiated-price state and retains its own Pareto archive and
stable preferred world.

## Fixed point and terminal precedence

One completed regeneration epoch is a fixed point only when all three values
are unchanged:

- the complete ordered pool roster and every immutable typed candidate value;
- every selected route's exact immutable candidate data, with candidate ID,
  provenance, policy, and pointer identity excluded; and
- the complete negotiated resource-price values, with iteration and state
  checksum excluded.

Terminal reason is evaluated in this precedence:

1. `resource_refinement_required` for any known unmapped exact conflict;
2. `feasible` when the current One-World or terminal preferred retained world
   selects every net with zero overuse;
3. `fixed_point` after the complete three-part predicate;
4. `regeneration_epoch_limit` after the configured final epoch.

No wall time, worker completion order, pointer identity, or lease identity can
change termination.
Pool-manifest checksums remain replay evidence, but never substitute for the
typed equality test. Equality disagreement between the manifest and typed
roster is an internal collision-or-drift error.

## Evidence and replay

Session counters retain completed epochs, planning visits, requested columns,
route queries and work, policy visits, generated/rejection/transient bytes,
and admitted, duplicate, rejected, novel, and changed-selection counts.

The representative corpus executes complete session ownership at requested
pool sizes 4, 8, and 16. A separately prepared globally coupled case also
compares the session's regenerated pools, price/world lineage, terminal worlds,
and authoritative CandidateStore against an independently composed targeted-
regeneration plus Multi-World execution.

The rejection manifest domain
`APGAR-CPU-CANDIDATE-ALLOCATION-REJECTIONS-V1` encodes every final canonical
Candidate Rejection v1 field in CandidateStore order.

The session checksum domain
`APGAR-CPU-CANDIDATE-ALLOCATION-SESSION-V1` encodes the complete semantic
configuration; Board, workload, capacity, and preparation identities; terminal
reason and all cumulative counters; every compact epoch and complete column;
final pool and rejection manifests; final price and One-World checksums; and
terminal Multi-World execution checksum. Addresses, lease IDs, worker count,
timing, and completion order are absent.
The two-net, four-candidate-per-net feasible representation fixture has session
checksum `10365567761333396631`. The prime-valued nonempty epoch/column fixture
has checksum `12912908603899075077`, and its complete optional-field rejection
manifest has checksum `15185300074143548732`.

## Deliberate boundary

This slice establishes the reusable CPU candidate-allocation contender and
its replayable terminal fixed-pool worlds. It does not implement a global
freeze/gather/publication epoch across multiple active world lineages, GPU
allocation, equal-budget timing, combined-route exact legalization, host-CAD
validation, or the Phase 4 evidence decision.
