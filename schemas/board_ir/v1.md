# Exact Board IR Schema v1

Board IR v1 is the normalized in-memory schema used by the first APGAR vertical
slice. Its implementation is `apgar/board_ir/board.h`.

## Snapshot header

- schema version: unsigned 32-bit integer, currently `1`
- database units per millimeter: required positive signed 64-bit integer; the
  core supplies no adapter-specific default
- revision: unsigned 64-bit integer
- adapter name and adapter version: non-empty UTF-8 strings
- deterministic content fingerprint: unsigned 64-bit FNV-1a over the canonical
  field encoding described below

The fingerprint detects accidental nondeterminism and associates compiled
artifacts with normalized content. It is not the replay bundle's future
cryptographic checksum.

## M1 entity tables

- Layer: stable entity reference, routing ID, name, physical order, signal type,
  and routability.
- Net: stable entity reference, name, and sorted terminal references.
- Terminal: stable entity reference, owning net reference, component/pin
  provenance, center, rectangular connection region, and sorted layer IDs.
- Obstacle: stable entity reference, layer ID, exact axis-aligned rectangular
  bounds, optional owning net, and required provenance.
- Routing profile: target two-terminal net, nominal width, clearance, sorted
  allowed layers, and H/V/45-degree heading mask.

Every entity ID is unique across all tables. References include the expected
generation and stale references are rejected. M1 snapshots contain exactly two
or four routable signal layers and exactly two terminals on the routed net. All
schema strings are valid UTF-8. Physical layer orders are unique and contiguous,
and every routed-net terminal has at least one connection layer allowed by the
routing profile.

## Prepared routing profiles

Board IR v1 publishes one normalized, authoritative routing-rule profile in
each immutable snapshot. Additional per-net obstacle-ownership contexts enter
exact compilation only through `PrepareRoutingProfile`. That boundary sorts
allowed layers, rejects duplicates, binds the result to the source snapshot's
content hash, and validates that:

- the target is a current net with exactly two current terminal references;
- nominal width and clearance are within the global exact-coordinate range;
- the heading mask is non-empty and contains only M1 headings;
- every allowed layer exists, is routable, and is a signal layer; and
- both routed-net terminals intersect at least one allowed layer.

Successful preparation returns an immutable `PreparedRoutingProfile` capability;
callers cannot construct that state directly. Exact consumers accept the
capability rather than a bare `RoutingProfile` and reject a source-content-hash
mismatch. Board IR v1 does not yet contain per-net rule tables, so every
prepared context must preserve the default profile's nominal width, clearance,
allowed layers, and headings. Only the target net may differ. The prepared
capability therefore authenticates canonicalization, snapshot membership,
Board-IR-authored M1 rules, and the net identity used for exact obstacle
ownership.

## Canonicalization and fingerprint

Before validation and publication, layers are sorted by routing ID, nets and
terminals by entity ID, and obstacles by `(layer ID, entity ID)` so immutable
per-layer obstacle spans are available to exact geometry. Terminal and layer
membership lists are sorted as well. The fingerprint encodes all fields in
schema order using fixed-width little-endian integers and length-prefixed
strings. Input table order therefore does not affect the normalized snapshot or
fingerprint.

The KiCad fixture adapter derives layer and net identities from their canonical
semantic names and terminal/obstacle identities from required KiCad object
UUIDs. Domain-separated 64-bit hashes and the content fingerprint use the same
shared stable-hash implementation; entity collisions are checked before
publication. Reordering fixture objects, including layer declarations, does not
change IDs or the normalized fingerprint; inserting an unrelated object does
not renumber existing entities. Layer physical order is derived from KiCad's
numeric copper-layer IDs (`0` for `F.Cu` through `31` for `B.Cu`), never from
declaration order.

## KiCad fixture input profile

- KiCad symbols and quoted strings remain distinct grammar types.
- Symbols reject embedded quotes, and exact decimal values reject a leading
  plus sign, a trailing decimal point, and more than six fractional digits.
- Footprints and pads require unique canonical lowercase UUIDs.
- Quoted strings must be valid UTF-8.
- Input is limited to 4 MiB, individual tokens to 4 KiB, nesting to 64 levels,
  and the parsed tree to 100,000 nodes.
- Every accepted metadata and geometry construct is shape-validated. Unknown or
  unsupported constructs fail explicitly.
- Net zero may be declared at most once. Copper layer IDs and names are unique
  and must agree with KiCad's front/back stack semantics.
- The adapter's fixed unit scale is 2,000,000 database units per millimeter.
  Import configuration supplies already-quantized widths and clearances in
  database units rather than reusing fixture-text parsing.
- SMD mask and paste layers must match the footprint copper side. Through-hole
  pads may use `*.Mask`; other ignored auxiliary layer spellings are rejected.
- Pad extents are checked against the coordinate envelope at the pad source
  offset before Board IR publication.

## Deliberate v1 limits

This first schema represents rectangular terminal regions and static
axis-aligned rectangular obstacles only. It does not yet serialize snapshots or
represent arcs, arbitrary polygons, existing tracks, vias, zones, rule regions,
or specialty-routing constraints. Unsupported adapter input fails explicitly.
