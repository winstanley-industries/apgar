# ADR-019: Phase 4 CPU Targeted-Regeneration Execution

**Status:** Accepted for the fifth Phase 4 vertical slice
**Date:** July 20, 2026
**Applies to:** Authentic CPU column generation, conditional store publication,
and deterministic progress or stall classification

## Context

ADR-018 produces a bounded store-backed hotset and an exact next-price policy
schedule, but a plan alone cannot establish that new columns were generated by
an authentic router, crossed exact admission together, remained available for
selection, or improved a board-level outcome. Per-column store calls would also
make worker completion order semantic, contrary to CAN-004.

The execution boundary must reject stale source pools and wrong-store leases
before mutation. It must also distinguish algorithmic stall from resource
exhaustion, invalid input, and known exact conflicts that the current allocator
resource vocabulary cannot represent.

## Decision

- Adopt `schemas/allocator/targeted_regeneration_execution_v1.md`.
- Execute a plan only while its CandidateStore-issued source lease is active
  and belongs to the exact store supplied to execution.
- Reproduce the complete source manifest, next negotiated-price snapshot, and
  next-price baseline selection before routing. Resolve each target only from
  the canonical `MultiNetWorkload`.
- Compare the complete expected source pools and their persistent per-net
  associations against the CandidateStore before any CPU query, then repeat
  the same conditional comparison under the final publication lock. Prepare
  and bound every target context and normalized policy schedule before routing
  the first target.
- Reject already-known source-roster, query, store-item, and policy-entry caps
  before proportional copies, reserves, or policy resource allocation.
  Enforce both the normalized primitive's exact per-target policy-entry cap and
  the execution configuration's complete-invocation cap.
  Refinement-only outcomes allocate no query or publication scratch.
- Generate every planned column through production CPU A*, then construct its
  draft only through the typed authenticated CPU candidate builder. Policies
  are the complete target-legal price projections defined by ADR-018;
  generators read an immutable snapshot and never mutate occupancy.
- Add a conditional CandidateStore invocation transaction. It accepts
  per-column authentic compiled views plus structured pre-admission failures,
  exact-admits all successful drafts, compares every declared source pool by
  complete immutable value under the publication mutex, and publishes all
  candidates and diagnostics through one CAN-004 boundary. Source drift fails
  without changing pools, rejection history, or publication telemetry.
- Rebuild complete canonical workload pools from the store after publication,
  run the production One-World CPU reference at the same next-price snapshot,
  and acquire a successor group lease over every refreshed winner before the
  plan lease is released.
- Classify the board-level result lexicographically: maximize selected nets,
  minimize total overuse, then minimize configured intrinsic quality. Stable
  terminal reasons distinguish feasibility, improvement, no targets, no
  successful generation, no novel retained column, unchanged selection, and a
  changed selection without objective improvement.
- Feasibility requires both zero overuse and no workload net lacking an
  admissible selected candidate. A zero-selection plan retains an empty
  store-issued identity lease so all-empty workloads can still validate drift
  and return a structured no-target outcome.
- A declared known unmapped exact conflict produces
  `resource_refinement_required` with no generation or candidate publication.
  It is never reported as feasibility, no work, or ordinary stall.
- Bind configuration, plan identity, refreshed manifests, baseline/refreshed
  worlds, ordered column outcomes, counters, and terminal classification into
  one versioned replay checksum. Runtime lease identities and timing are not
  replay fields.

## Consequences

- One deterministic CPU invocation may contain authentic candidates from
  multiple nets and rule buckets without splitting publication by compiled
  view or worker completion order.
- A plan cannot be replayed against a different store or against an extra,
  missing, replaced, or semantically mismatched source candidate.
- Selected candidates remain pinned across the plan-to-refreshed-world handoff;
  independent plan and successor leases may overlap safely.
- Execution is bounded by route-query, compiled-state work, policy-entry,
  store-transaction, allocator, and successor-lease limits. Failures before
  publication leave the store unchanged. Callers must serialize other
  CandidateStore mutations with one synchronous execution invocation.
- This CPU reference does not add GPU generation, combined-route legalization,
  or host-CAD validation. Multi-world retention, the Phase 4 corpus, and
  equal-budget evidence remain open work.
