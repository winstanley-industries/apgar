# ADR-069: Deterministic CPU Candidate-Pool Preparation

**Status:** Accepted for P4R-04

**Date:** August 4, 2026

**Applies to:** EPIC-001 P4R-04 production CPU candidate-pool preparation

## Context

P4R-03 consumes explicit immutable per-net candidate pools but deliberately
does not construct them. Phase 3 already supplies the production CPU A* route
generator, deterministic alternative-policy schedule, authenticated candidate
builder, exact admission, and CAN-004 CandidateStore batch publication. P4R-04
must compose those authorities for multiple prepared-net compiler contexts
without creating another candidate representation, another geometry oracle, or
allocator state mutation inside route generation.

The composition also needs explicit resource ceilings. A bounded worker count
alone does not bound the number of queries, A* work, draft bytes, retained
bytes, or exact-admission transaction work. Publication after each worker would
make retention and diagnostics depend on completion order, while publishing
before all fatal outcomes are known could expose partial pools.

## Decision

- The preparer accepts one immutable BoardSnapshot, one explicit retained
  CompiledBoard and planar request per requested net, and one explicit
  deterministic alternative-policy schedule per net. Exactly one schedule is
  required for each requested net.
- Net schedules are canonicalized by EntityRef. Alternative resources continue
  through the Phase 3 policy normalizer, so caller order and duplicates do not
  define policy, query, or candidate identity.
- Production CPU A* gains an explicit deterministic work-unit limit. Its v1
  vocabulary counts queue pops, expanded states, attempted relaxations,
  reconstructed states, and exact segment validations. Equality is accepted;
  the next unit returns a typed resource failure marked as work-limit
  exhaustion.
- The preparer preflights positive hard configuration bounds and configured
  ceilings for net count, candidates per net, total queries, per-query and
  aggregate CPU work, per-query and aggregate generated bytes, aggregate
  retained capacity, and CandidateStore transaction limits. All aggregate
  arithmetic is checked before workers start.
- An explicit bounded number of workers claims canonical query indices. A
  worker may invoke only production CPU A*, authenticated candidate
  construction, and source-private test hooks, then fill its own canonical
  result slot. Workers do not publish, mutate CandidateStore, update occupancy
  or prices, or mutate Board IR and compiler state.
- Disconnected and currently unsupported routes are ordinary canonical draft
  diagnostics. Candidate-builder and exact-admission rejection are also
  ordinary column outcomes. Work-bound exhaustion, host resource exhaustion,
  association failure, arithmetic overflow, and internal invariant failure are
  fatal typed preparation outcomes.
- After every worker completes and all actual aggregate bounds pass, one fresh
  local CandidateStore consumes every successful draft and every ordinary
  rejection through one mixed-draft batch transaction. CandidateStore binds
  the common Board/compiler resource lattice across the batch and retains one
  complete immutable exact-admission association per net. Thus distinct
  prepared-net profiles can publish together without permitting association
  drift within a net pool.
- The fresh store is not externally visible. Any fatal outcome after worker
  execution destroys it with the preparation scratch, so the API returns
  either the complete immutable set of canonical per-net pools or no pools.
- Every requested net appears exactly once in the output, including an explicit
  empty pool when no candidate is admitted. Stored candidates are exposed in
  CandidateStore rank order and through a direct P4R-03 OneWorldCandidatePool
  view. Columns and diagnostics use canonical net/policy/query order.
- Exact-small tests maintain a sequential reference composition that directly
  invokes the existing Phase 3 normalize, route, build, and admit primitives.
  It does not call the production preparer.

## Consequences

- Worker-count and completion-order changes may affect timing but not candidate
  identities, retained pools, columns, diagnostics, or accounting totals.
- CandidateStore's store-wide binding is the common physical resource lattice,
  while its per-net binding remains the complete association tuple. Existing
  stale-board and same-net drift protection remains fail-closed.
- P4R-04 adds no reusable allocation session. A later task that needs persistent
  pools must define its own lifetime and mutation contract rather than treating
  this local transaction as hidden session state.

## Explicit non-goals

This decision does not add P4R-05's sequential negotiated-routing baseline,
prices, negotiated routing, targeted regeneration, Multi-World, GPU allocation,
reusable allocation sessions, serialized evidence, runners, telemetry
publication, or campaign infrastructure. It does not import the archived
candidate-pool preparer.
